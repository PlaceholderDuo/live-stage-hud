═══════════════════════════════════════════════════════════════
THE NEW FORMAT
═══════════════════════════════════════════════════════════════

{title: Song Title}
{artist: Artist Name}
{key: Gm}
{bpm: 94}

## Chorus 1 @0.0
  [Gm]I [Cm]shot [Gm]the sheriff, but I did not shoot the deputy @2.0
  [Cm]I [Gm]shot the sheriff, but I did not shoot the deputy @4.0

## Verse 1 @16.0
  /Bb/Eb Dm7 Gm/
  All around in my home town @16.0
  /Bb/Eb Dm7 Gm/
  They're trying to track me down @24.0

RULES:
  1. ## starts a section header. Name followed by optional @seconds.
     Section type is auto-detected: "Chorus" → chorus, "Verse" → verse,
     "Solo" → solo, "Bridge" → bridge, "Intro" → intro, "Outro" → outro.
  2. Content lines start with 2 spaces (visual indent, stripped by parser).
  3. @seconds at end of a content line is the timestamp (float, no "=").
  4. /Chord1 Chord2/ wraps bare chord rows (no lyrics). Parser merges
     these into the next lyric line automatically.
  5. Metadata directives stay as {key: value} at the top of the file.
  6. No {end_of_*} directives — the next ## header implies previous ended.
  7. No @bar=N — bar position is derived from @time + BPM in code.
  8. No @time= prefix — just @N.N (the "=" served no purpose).

═══════════════════════════════════════════════════════════════
JAVASCRIPT PARSER REFERENCE (UPDATED 2026-07-30)
═══════════════════════════════════════════════════════════════

File: web/public/hud.js — function parseChordPro(text)

Detection: if ANY line starts with ## → isNewFormat = true

Key behavior:
  - Lines starting with ## → section header (extracts label + @time)
  - Lines starting with { → metadata directives
  - Lines starting with /text/ → bare chord markers (unwrapped)
  - Content lines: extract trailing @N.N, unwrap /bare chords/

IMPORTANT — Backward Compatibility Fallback:
  The migration was NOT perfectly clean. Some lines in new-format
  files still have old @time=N @bar=N prefixes (e.g., songs like
  "I Shot the Sheriff", "Come Together", "Wild Horses").

  The parser handles this with a fallback in the isNewFormat branch:
    1. Try trailing @N.N extraction (lastIndexOf("@"))
    2. If null, try old @time=N regex as fallback
    3. Strip both old and new annotations from content text
    4. Unwrap /bare chord/ markers

  DO NOT REMOVE THIS FALLBACK. It is load-bearing for ~40 songs
  where the migration left mixed old/new annotations.

  Without the fallback: 42/43 lines in "I Shot the Sheriff" lose
  their timing and fall through to estimateLineTimes().

  With the fallback: 24/28 lyric lines correctly timed in same file.

This pattern exists in THREE parsers — all must stay consistent:
  hud.js          parseChordPro()       — HUD client display
  server.js       extractLyricLines()   — sync health + lyric API
  verify-lyric-sync.js parseChoproLines() — verification tool

  All three now have:
    1. Try trailing @N.N (for clean new-format lines)
    2. Fallback to @time=N regex (for mixed-format lines)
    3. Strip both annotation types from cleaned text

Old format fallback: if no ## lines detected anywhere in the file,
uses @time=N regex + {start_of_*} / {end_of_*} parsing exclusively.

post-processing: bare chord rows (all tokens are chord names)
get their chords merged into the next lyric line via
isChordOnlyLine() → pendingChords[] → merged pairs.

═══════════════════════════════════════════════════════════════
PARSER RULES FOR ANY NEW CODE
═══════════════════════════════════════════════════════════════

When writing a NEW chopro parser (e.g., in Lua for runner.lua):

  1. Skip lines starting with ## (section headers)
  2. Skip lines starting with { (metadata)
  3. Skip /bare chord marker/ lines
  4. For content lines:
     a. Try trailing @N.N: match /\s@([\d]+\.?\d{1,2})\s*$/
     b. If no match, try old prefix @time=N: match /@time\s*=\s*([\d]+\.?\d*)/
     c. Strip: /@time\s*=\s*[\d]+\.?\d*/gi, /@bar\s*=\s*\d+/gi, /\s@[\d]+\.?\d{1,2}\s*$/g
     d. The cleaned text is the lyric content
