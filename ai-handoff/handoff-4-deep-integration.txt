═══════════════════════════════════════════════════════════════
PRIORITY 1: Push-Mode Lyric Selection in Lua Runner
═══════════════════════════════════════════════════════════════

Current: The HUD client parses the chopro file, finds current
line by comparing _time against position. This means:
- Every HUD client re-parses the chopro independently
- If a client reconnects mid-song, it re-fetches and re-parses
- Zero verification that the line shown is correct

Target: The REAPER Lua runner (60fps) pre-parses the chopro at
song load, does a binary search for current line on each frame,
and publishes `currentLine` + `currentSection` + `totalLines`
in bridge_state.json. The HUD uses these directly.

Files to change:
  A) runner/runner.lua (~/Library/App Support/REAPER/Scripts/
     Live Show Manager/runner/runner.lua, 320 lines)
  B) runner/bridge.lua (88 lines)
  C) web/server.js — read + broadcast new fields
  D) hud.js — prefer currentLine/section from state over parsing

Step-by-step for the runner:

A.1) Add a chopro parser to runner.lua:
  - On song change (region change or first tick), load the
    song.chopro file via io.open()
  - Parse @time=N annotations into a sorted table:
    lyricLines = { {time=3.52, text="...", bar=19}, ... }
  - Store as a global or module variable

A.2) Per-frame lookup (every ~16ms):
  - Get current position from REAPER (already done)
  - Binary search lyricLines for the line where time <= position
  - Set currentLineIdx = index of that line
  - Find currentSection from Show.lookupBySection or from
    section boundaries in the region table

A.3) Publish via bridge.lua:
  - Add to the bridge_state.json payload:
    { currentLineIdx, totalLines, currentSectionIdx, currentSectionName }

B) Bridge.lua changes:
  - Add currentLineIdx, totalLines, currentSectionIdx,
    currentSectionName to the published table

C) Server.js changes:
  - In poll loop, read new fields from bridge_state.json:
    state.currentLineIdx = luaState.currentLineIdx
    state.currentSectionIdx = luaState.currentSectionIdx
    state.currentSectionName = luaState.currentSectionName
  - These get automatically broadcast via broadcastState()

D) HUD changes:
  - In socket.on("state"), if s.currentLineIdx is present:
    lyricEngine._currentLineIdx = s.currentLineIdx
    Use it directly in renderRollingEngine instead of
    recomputing from _time lookup
  - Fallback to current time-based lookup if currentLineIdx
    is not present (backward compat)
  - Log the index source for debugging:
    _d.textContent += " src=" + (s.currentLineIdx ? "lua" : "client")

E) Optional: HUD accepts the line index as authoritative:
  - renderRollingEngine receives currentLineIdx directly
  - Draws the 6-line window centered on that index
  - No time comparison needed — the Lua runner already did it

PRIORITY 2: Song Library Cleanup
═══════════════════════════════════════════════════════════════

Current state (verify-lyric-sync.js):
  - 258 songs with @time=N annotations
  - 61 songs with ZERO annotations
  - The 61 are mostly: OFFICIAL ... TABS duplicates,
    CHORDS (ver N) variants, slug-named GP imports

Cleanup steps:

A) Identify duplicates — the verify script already reports
   "No timing" songs. Many are duplicates where the clean
   version (e.g., "Aint No Sunshine") already has @time=N,
   and the "OFFICIAL AINT NO SUNSHINE TABS" variant doesn't.

B) Merge before deleting:
  - For each pair (e.g., "Aint No Sunshine" vs "OFFICIAL
    AINT NO SUNSHINE TABS"), compare chopro quality:
    * Which has more lyric lines?
    * Which has chord annotations ([] brackets)?
    * Which has real BPM (not 120)?
  - Keep the best, delete the duplicate
  - If both have useful info, merge: copy chords from one
    into the other's chopro, then delete the inferior

C) Handle slug-named songs:
  - Songs like "cant_you_see", "highway_to_hell", "limelight",
    "papa_was_a_rollin_stone", "whole_lotta_rosie" have very
    few annotated lines (1-7). These were likely GP imports
    that only got partial annotations.
  - Check if a clean-named version exists (e.g., "Can't You See")
  - If not, rename the folder to a clean title
  - If lyrics are sparse, flag for later lrc-to-bars processing

D) Standardize folder names:
  - Strip "OFFICIAL", "TABS", "CHORDS (ver N)" from folder names
  - Standardize to: "<Song Title>" without version suffixes
  - Update meta.json title field to match folder name

E) Final state target:
  - 0 songs with "OFFICIAL" or "TABS" or "CHORDS (ver" in name
  - Every song has either @time=N annotations or is flagged
    as "needs LRCLIB" in a small list
  - No duplicate songs (verified by title + artist similarity)

PRIORITY 4: Pre-Show Checklist (iPhone Page)
═══════════════════════════════════════════════════════════════

Add a "Checklist" page to the iPhone controller that runs
before showtime. The page:

A) Checks server health:
  - LSM :3000 reachable?
  - iPhoneLiveServer :3300 reachable?
  - REAPER connected? (bridge_state.json age < 5s)
  - MIDI virtual port "Live Show Manager" exists?

B) Checks setlist sync health:
  - Runs verify-lyric-sync.js --json for songs in active setlist
    (via child_process.exec on the server, exposed as
     /api/preflight endpoint)
  - Shows per-song results: green dot (100% @time), yellow
    (80-99%), red (<80%)
  - Aggregate score: "8/10 songs ready"

C) Checks network:
  - WiFi connected?
  - Bonjour hostname resolves?
  - Dell reachable at 192.168.0.127?
  - Cloudflare Tunnel URL (if running)?

D) Result display:
  - Green banner: "ALL SYSTEMS GO — 10/10"
  - Yellow banner: "⚠ 2 ISSUES — proceed with caution"
  - Red banner: "✗ 4 ISSUES — fix before showtime"
  - Each issue tappable for details
